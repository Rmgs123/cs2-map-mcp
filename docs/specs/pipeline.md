# Fast loop: packages, regions, offline preview, face index

A small change on a big map is answered in seconds: only the changed packages are replayed, only the stale generators run, one zone is built and loaded instead of the map, the saved map is drawn without the game, and the scene checks keep what they found. None of it may differ from a full replay and a full build. Code: `pipeline.py` (packages, manifest, the job), `genrun.py` (generator runner), `project.py` (`map_edit` markers, `map_apply`, `packages_state`), `region.py`, `faceindex.py`, `preview3d.py`, `visual.py` (`_findings`, `_audit`, `_fair_share`, `_zones`), `checks.py` (`scene_cache`). Guide for models: `docs/tools/pipeline.md`.

## Packages

**The record in the map.** `map_edit` accepts `{"op": "replace_batch", "tag": T, "hash": H, "needs": [...]}` anywhere in a batch: the nodes carrying `cs2map_batch = T` are removed, and the root of every subtree made until the next marker gets the tag. `{"op": "replace_batch", "remove": [tags]}` only removes. The world node keeps `cs2map_packages`: `{order: [tags], packages: {tag: {hash, needs, touches, ops, nodes}}}`. `touches` are the packages whose nodes this one looked up or changed: `VMap.tracker` is called by `VMap.node` and by a lookup by name while a package runs, and `_owners` maps a node id to the tag of its nearest tagged ancestor. `nodes` is counted once after the whole call (a later package may remove nodes of an earlier one).

**The plan** (`pipeline.plan`). A package is replayed when its hash differs, it is new, or the number of its tagged nodes in the map is not the recorded one (hand edits). Then to a fixed point: a package with declared `needs` is replayed when a needed or touched package is; a package without `needs` (or one that touched nodes of no package) is replayed when any package before it is, or when the order of the kept packages changed; a package whose nodes a replayed package touched is replayed too (its nodes carry that package's changes). The hash covers the operations (canonical JSON), the declared `needs` and the tools' version. Each record also keeps `game`, a digest of the game's FGD files (`fgd.signature`): a package applied under other entity definitions is replayed (12.11: a CS2 update added a keyvalue to `info_map_parameters` and a map built the day before differed from a clean replay in one package). A map with more than 40 nodes of no package and no package record is refused, not added to (a 24 500-node map built earlier from the same files by plain `map_edit` calls would have been doubled); a bare `{"op":"replace_batch","tag":"base"}` call leaves a record and keeps those nodes on purpose.

**The apply** (`pipeline.apply`). One `map_edit` call: a `remove` marker for every package to replay or drop, then each package behind its marker in list order. `PACKAGE_CALL` lifts the 2000-operation limit for this call and makes the recorded order that of the list. An undeclared touch of another package is an error naming both. Nothing is saved when any operation fails; the error names the package and the operation's index in it. A plain file list that leaves out a recorded package is refused; a manifest (`complete=True`) removes it.

**Clean replay** (`pipeline.verify`, `canonical`). `dry_run` replays every package into a fresh map from the same template (`cs2map_template` on the world node) and compares digests per package: node ids, reference ids, the package record and `randomSeed` are left out, children are sorted by digest, floats are compared as the 32 bits the file stores. `.local/state/pipeline.json` counts partial updates per map; `release_gate` refuses `map_build(..., "release")` while the count is not zero, and a passed dry run or a whole replay clears it. `map_create` forgets the record.

**The job.** `map_edit(packages=...)` starts `python -m cs2map.pipeline <spec>` through `jobs.py` (low priority as other builds, cancel, recovery after a server restart). A lock file per map (`.local/locks/pipeline-<addon>-<map>.lock`, pid and time) makes a plain `map_edit` of another process refuse while the job rewrites the map.

**The manifest** (`pipeline.run`). Steps in order. `run`: the script is started by `genrun.py` under an isolated interpreter (`-s -P`, no `PYTHON*` variables of the user, UTF-8, `PYTHONHASHSEED=0`: a set of strings iterates alike in every run — a generator looping over `set(materials)` wrote another order of operations each time and its package looked changed) in its folder; an audit hook notes every file opened for reading and every module loaded from a file; those inside the folder are hashed into `.pipeline/state.json`. The step is stale when its key (tools' version, script hash, `args`, hashes of `inputs`) or a noted file changed, or a package file is missing. A file the script looked for and did not find is noted too. The steps are passed again (at most 3 times) while a generator that ran left an earlier step stale — a step may read what a later one writes (12.11: kerb, skirt and fence generators of a town map read the package of a later hill generator and had seen the previous run's file); the result's `unsettled` names generators that never settle. File hashes are kept per (path, time, size) for the job. `tool`: a public MCP tool (`surface.PUBLIC`, the functions AI clients call) called with `args` (inline or a JSON file) when the arguments' digest changed; tools that edit, build or start the game are refused. Then one `apply` of every listed package.

## Region builds

`region.build`: load the saved map (a private copy), `region.cut`, save as `<name>_region` without backups, start the usual build. `cut` walks the tree: a mesh is dropped when its box misses every region box by more than 384 units, kept when inside; a mesh that crosses the border with more than 64 faces is rewritten with only the faces whose box touches the region + 384 (`_subset`: decode with `meshops`, rebuild through `Mesh`, carry UV, tint and blend per face corner; a cut that cannot be rebuilt keeps the mesh whole); smaller ones are kept when within 64 units. Point entities are kept within 64 units, brush entities by their meshes, groups by their children; sun, sky, fog, tonemap and post-processing always. Two spawns are added at the centre of the first box when none is inside (a player in the void makes black frames). `regions.json` in `.local/state` records source, boxes and preset; `game_screenshot` makes the frames of a region built without light fullbright. The slot `<name>_region2` is used while CS2 holds the first compiled file, so the game needs no disconnect.

## The face index

`faceindex.extract` reads every mesh node with numpy: half-edge loops to padded index rows (`face_loops`), fans (`triangles`), a material per face, flags per node (`SOLID`, `RENDER_ONLY`, `TOOL`, `SCENERY`), and the props with their measured boxes. `faceindex.scene(project, name)` keeps the result in `.local/cache/faces/<addon>/<map>.npz` (limit 600 MB, oldest first) and uses it again while the map file and its layer prefabs have the same size and time: the preview of an unchanged map does not parse the map.

Scene checks work on node objects and Python triangles; `checks.scene_cache()` (opened by `visual._audit`) shares the vertices, triangle lists and triangle arrays of a mesh between the checks of one audit. The vertex transform and the normal tests on arrays use the arithmetic of the scalar code in the same order, so the findings are the same ones. `visual._findings` keeps all findings of a map (and of each zone) in `.local/cache/checks/` with a key of the map file, its layers, the compiled files of its own models, the notes files and the check code's own files; `check_map` reads the same cache.

## Offline preview

`preview3d.render`: triangles from the face index, a colour per material (the average of its colour texture when the source is readable, else by words in its name, cached in `.local/cache/material_colors.json`), props as boxes, plants as stippled boxes, tool faces left out. Perspective views use the game's field of view (90° at 4:3, widened to the picture's aspect) with the eye 64 units over `pos`; triangles are clipped at the near plane; a z-buffer rasteriser in numpy works in chunks of pixel candidates. `top` and `side` are orthographic and report `units_per_pixel` and the ranges shown. Shading: one sun from the map's `light_environment`, an ambient term, an outline where the object or the depth changes.

## Why it is built this way

- The package record lives in the map file, not beside it: a restored backup, a copied map or a map edited by another client still knows what it holds.
- Dependencies are observed (`touches`), not trusted: a forgotten `needs` is an error at the first apply, not a stale zone weeks later.
- Hand edits inside a package are found by the node count, cheaply; edits that keep the count are found by the dry run, which a release requires.
- A region is cut from the saved map by one code path and written under another name: it cannot drift from the map, and nothing made for speed is ever read back.
- Caches are keyed by content or file stamps plus the tools' version and are safe to delete; every one has a size limit.

## Pitfalls we hit

- `VMap.remove` used to drop the whole id table: 24 000 new nodes then cost a walk of the map each (minutes). The tables now lose only the removed subtree.
- A map loaded from disk stores floats as 32 bits; the same map in memory has doubles: digests are taken over 32-bit values.
- `randomSeed` of some nodes is a fresh random number per run: left out of the comparison.
- A region without a spawn inside gives black frames (the player falls); a `fast` region without fullbright hides objects in unbaked shadow.
- The zone check used to audit phantoms, lamps and fences against the zone's solids only: walls outside the zone were reported as having nothing behind them. A zone is now audited with its surroundings and findings are kept by their place.
- Checks that add up samples along a mesh (paved slab, gap and lip, bare clip) read bare ground where a long road left the loaded surroundings, and the worst place then lay outside the zone: the finding was lost. `visual_scene.Zone` makes them count the samples in the zone only (`reports`), and a stray piece of paving is judged only when its whole outline is loaded (`known`). On the town map two zones of 2400 × 2400 units gave exactly the full audit's findings placed in them (829 and 397), none more.
